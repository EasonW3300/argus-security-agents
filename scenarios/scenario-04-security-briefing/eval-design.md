# 场景 4 Eval 评测集设计 —— 任务简报生成及推送

## 概述

场景 4 是**报告生成型 Agent**，与前三个场景的核心差异是——评测重心从"推理质量"转向**数据搬运准确性+模板完整性+受众适配+脱敏+推送准确**。

采用路线 A：mock 源数据 + 模板定义注入 prompt，LLM 一次性生成结构化简报。

## 需求摘要

| 能力 | 描述 |
|------|------|
| 数据提取 | 从 mock 安全数据源中提取关键指标（告警总数、趋势、高危分布、处置率等） |
| 模板填充 | 按预设模板填充所有必要字段，不遗漏、不篡改 |
| 格式合规 | 输出 Markdown 格式，章节结构、标题层级、表格列对齐 |
| 敏感信息脱敏 | 面向管理层的简报：脱敏具体 IP、漏洞 POC、受影响资产名称；面向安全负责人：保留完整信息 |
| 推送准确 | 简报是否推送到正确的 channel/人 |

## 与场景 1/2/3 的差异

| 维度 | 场景 1 | 场景 2 | 场景 3 | 场景 4 |
|------|--------|--------|--------|--------|
| Agent 类型 | 工具调用型 | 研究型（RAG） | 工具编排型 | **报告生成型** |
| 原型路线 | 路线 A | 路线 A | 路线 B | **路线 A** |
| 核心评测对象 | 研判质量 | 忠实度+引用 | 工具选择+编排 | **数据准确性+模板完整性+脱敏** |
| Mock 数据结构 | API 返回体 | 检索 chunks | 多步 tool responses | **源数据 + 模板 + 推送目标** |
| 代码型 Grader | 5 个 | 4 个 | 5 个 | **6 个** |
| 模型型 Grader | 2 个 | 3 个 | 2 个 | **2 个** |

## 评测维度（CLEAR 定制化）

| 维度 | 指标 | 目标阈值 |
|------|------|---------|
| **Efficacy** | 数据准确率（简报数值与源数据一致） | ≥99%（零容忍） |
| **Efficacy** | 模板填充完整率 | 100% |
| **Efficacy** | 格式合规率（Markdown 结构正确） | ≥95% |
| **Efficacy** | 推送目标准确率（channel+接收人） | 100%（零容忍） |
| **Latency** | 生成耗时 | ≤5 分钟 |
| **Reliability** | 定时任务执行率 | ≥99.5% |
| **Assurance** | 敏感信息脱敏率 | 100%（管理层视图零容忍） |

## Mock 数据源 + 模板结构

每条测试用例包含三部分 mock 数据：
1. **源数据**（模拟从 SIEM/工单/漏洞系统提取的原始数据）
2. **模板定义**（简报的章节结构、必须填充的字段、格式要求）
3. **推送配置**（目标受众、渠道、脱敏要求）

### 源数据类型

| 数据类型 | 字段 | 用途 |
|---------|------|------|
| 告警统计 | 时段内告警总数、各级别分布（critical/high/medium/low）、同比变化率 | 态势总览 |
| 告警处置 | 已处置数、处置率、平均处置时长、待处理队列 | 处置进展 |
| 漏洞统计 | 新增漏洞数、高危/中危/低危分布、已修复数、修复率 | 脆弱性管理 |
| 安全事件 | 事件 ID、类型、受影响资产、处置状态、时间线 | 事件详情 |
| 威胁情报 | 新增 IOC 数量、命中告警的 IOC 数、活跃 APT 组织 | 情报动态 |

### 简报类型

| 类型 | 受众 | 特点 |
|------|------|------|
| 日报 | 安全负责人 | 数据密集，含具体 IP/资产名/漏洞编号，操作导向 |
| 周报 | 安全负责人 + 管理层 | 趋势分析 + TOP 风险，管理层版本需脱敏 |
| 月报 | 管理层 | KPI 仪表盘 + 同比趋势 + 整改建议，高度脱敏 |
| 专项报告 | 安全负责人 | 某次安全事件复盘、护网行动日报，含技术细节 |

## Agent 输出格式

```json
{
  "report_title": "string",
  "report_type": "daily|weekly|monthly|special",
  "target_audience": "security_lead|management|both",
  "target_channel": "email|slack|dingtalk|wecom",
  "target_recipients": ["string"],
  "content": {
    "sections": [
      {
        "title": "string（章节标题）",
        "body": "string（Markdown 格式正文，含表格/列表）",
        "data_source_mapping": {"指标名": "源数据中的具体字段路径"},
        "data_values": {"指标名": "该字段未经格式化的实际 JSON 值（内部审计）"}
      }
    ]
  },
  "masking_applied": [
    {"original": "string", "masked": "string", "rule": "string"}
  ],
  "metadata": {
    "generated_at": "ISO8601",
    "data_sources_used": ["string"],
    "push_status": "sent|queued|draft"
  }
}
```

`data_source_mapping` 始终保存“指标名 → 源字段路径”，不能存放数值；`data_values` 以相同指标名保存实际值。每个模板章节的 `required_data` 都必须在该章节映射中出现，正文还要显式声明对应指标和值（管理层可声明 `masking_applied` 中记录的脱敏值）。

`data_values` 和 `masking_applied.original` 是评分审计字段，不属于管理层可见简报；脱敏 Grader 因此扫描正文、展示标题、来源路径映射和元数据，而不把合规审计字段视作泄漏。

## Grader 设计

### 代码型 Grader ×6

| Grader | 逻辑 |
|--------|------|
| `data_accuracy` | 提取简报中的所有数字指标，与 mock_source_data 中的对应值逐一比对。允许±0.1%的浮点舍入误差，但不允许逻辑不一致 |
| `template_completeness` | 检查模板定义的每个 section 是否存在且非空；检查每个 `{{placeholder}}` 是否被真实数据替换 |
| `format_compliance` | 检查输出是否为合法 Markdown：标题层级不跳级，表格列对齐，代码块配对，列表缩进一致 |
| `masking_check` | 管理层受众：检查 content 中是否出现 IP 地址（正则）和 ground_truth.sensitive_patterns 中定义的模式。安全负责人受众：验证这些信息是否被保留而非错误脱敏 |
| `push_target` | 检查 `target_channel` 和 `target_recipients` 是否与 push_config 完全匹配 |
| `output_schema` | 输出为合法 JSON，包含 report_title/report_type/target_audience/target_channel/target_recipients/content/metadata |

### 模型型 Grader ×2

| Grader | 评分维度 |
|--------|---------|
| `language_quality` | 1-5 分：文字表达是否专业简洁、受众适配是否准确（管理层版避免技术黑话，安全负责人版保留技术精确度） |
| `insight_quality` | 1-5 分：是否包含有价值的趋势分析而不仅是数据罗列——数据解读+趋势判断+可操作的后续建议 |

### 人工型 Grader ×1

| Grader | 触发条件 |
|--------|---------|
| `spot_check` | 每 8 条随机抽 1 条，从接收者视角评估简报的可读性和价值密度 |
